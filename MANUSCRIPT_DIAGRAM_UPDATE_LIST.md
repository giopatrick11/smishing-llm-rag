# APCIDA diagram update list

Source: `Manuscript - ApCiDa (1).pdf` PDF pages 26–29, 32–34, 55–56, 62–73. Specifications below reconstruct **current checked-out code**, not the older diagram artwork. Path shorthand: `A/` = `.tmp-mobile-notification-fix/app/src/main/java/com/apcida/smishingdetector/`; `S/` = `apcida-ai-server/src/`. Supervised beta remote inference is source-wired but actual live deployment was not checked. The debug-only MediaPipe path must be a separate historical/experimental diagram if retained. "Valid" evaluates the old figure for describing this beta.

## 1. IPO model — Fig. 1, §2.5.1, PDF pp.26–27 — P0

**Valid:** No. **Outdated components:** threshold-gated on-device Gemma, final SAFE below threshold. **Missing:** beta gate, enrollment and AI consent, local provisional state, authenticated remote API, server embedding/RAG/Gemma, timeout, report consent. **Incorrect arrows:** Stage 1 score must not decide whether an *eligible* new message is sent to AI; report text crosses the network after separate consent. **Storage/boundary correction:** Room on Android; knowledge/inference/report stores in PostgreSQL on server. **RAG/backend effect:** RAG precedes Gemma chat for beta, with top-three approved examples above 0.72 similarity (`S/db/knowledgeRepository.js -> search`; `S/production/createProductionApp.js -> createAnalysisService`).

**Replacement specification:** Inputs = incoming SMS text/sender/time, built-in Android rule policy, AI consent/enrollment and build gate, server approved RAG knowledge/model, optional report/study consent. Process = SMS receiver → local rule score and provisional Room row → local warning if rule SCAM → if eligible, WorkManager → authenticated HTTPS API → embedding → approved-example cosine retrieval → Gemma 3 12B JSON response with shadow server rules → mobile verified result; on error/timeout retain local warning or `UNVERIFIED`. Outputs = verified `SAFE`/`SUSPICIOUS`/`SCAM` or provisional/`UNVERIFIED`, conditional notification/rationale/confidence, optional separately submitted report and study record. Evidence: `A/backend/receiver/SmsReceiver.kt`, `A/controller/SmsController.kt`, `A/backend/worker/SmsProcessingWorker.kt`, `S/services/rag.js`, `S/services/ollama.js`.

## 2. Business Process Model — Fig. 2, §2.5.1, PDF pp.28–29 — P0

**Valid:** No. **Outdated components:** user, app and one “Data and Log Store” conceal network actors; local Gemma 2B and anonymized report are incorrect. **Missing:** Android OS, enrolled phone/consent, controlled API, Ollama, PostgreSQL, admin review. **Incorrect arrows:** `SAFE` local rule path is not a final verified SAFE; report payload includes SMS text. **Storage/boundary correction:** separate Room, PostgreSQL inference cache, production reports and RAG knowledge; admin review never automatically converts a report into knowledge. **RAG/backend effect:** retrieval and inference are server activities. Evidence: `A/backend/network/RemoteVerdictPolicy.kt`, `A/backend/network/ReportApiService.kt`, `S/production/reportReviewCli.js`.

**Replacement specification:** Swimlanes: Mobile User | Android OS | Android app/Room | controlled APCIDA server | Ollama | PostgreSQL | Admin/researcher (only for review/study). Begin permission/enrollment/AI consent → OS delivers new SMS → app computes local rule and stores provisional row → rule SCAM may warn immediately → gate decision. If closed/unavailable: show local rule warning or `UNVERIFIED`. If open: send consented raw text/sender to server → retrieve/LLM → return verified class → update Room/notification. Optional fork: user opens report form and confirms separate text-sharing consent → local queue → authenticated report API → encrypted report row → admin review/staging/approval. Optional study fork: selected historical items require separate participant consent and study endpoint. Label all cross-boundary arrows with exact data categories.

## 3. DSR framework — Fig. 3.1, §3.2, PDF pp.32–34 — P1

**Valid:** Partially: DSR stages remain a research structure; the artifact and evaluation annotations are obsolete. **Outdated components:** “keyword + on-device Gemma 2B + SQLite” as complete build. **Missing:** supervised beta server/RAG, explicit consent and data flow, separate synthetic development and independent participant study. **Incorrect arrows:** Evaluation should not flow from all committed synthetic results to final real-world validity without participant evidence. **Storage/boundary correction:** annotate local Room and server PostgreSQL as separate built artifacts. **RAG/backend effect:** show model/RAG comparison as one technical evaluation branch; user study is a distinct branch. Evidence: `S/production/createProductionApp.js`; `S/evaluation/threeClassStudy.js`; `S/study/worker.js`; `S/db/migrations/009_study_contributions.sql`.

**Replacement specification:** Problem/motivation → objectives → design/build (Android local screening + controlled backend + RAG + data protection) → demonstration (synthetic and supervised beta separately) → evaluation A (committed synthetic binary-ground-truth and 8-case three-class exploratory results), evaluation B (participant study only when completed), usability evaluation (pending unless records supplied) → communication/iteration. Each evaluation node names dataset, version and status “completed” or “planned”; indicate rule v2 Android and v3 server shadow divergence as an iteration issue.

## 4. Activity diagrams — Fig. 4.1.1, PDF p.55, and §4.3.1, pp.62–64 — P0

**Valid:** No for beta. **Outdated components:** high-score-only local Gemma and unconditional safe notification. **Missing:** consent, build/credential/HTTPS gate, WorkManager job, provisional state, remote API, unavailable/expired state and verified update. **Incorrect arrows:** threshold branches should control local warning severity, not remote eligibility. **Storage/boundary correction:** Room writes before and after remote call; server inference is a distinct activity partition. **RAG/backend effect:** server embeds and retrieves before chat, with empty-hit path still reaching Gemma (`S/services/rag.js`). Evidence: `A/controller/SmsController.kt -> receiveAndAnalyzeRules/applyRemoteResult`; `A/backend/worker/SmsProcessingWorker.kt`; `S/production/createProductionApp.js`.

**Replacement specification:** Start → SMS broadcast → assemble multipart body → deduplicate → rule v2 analysis → persist Room provisional row → [rule SCAM? local warning] → [beta enabled + enrolled + AI consent + new SMS + approved HTTPS?] → no: local verdict `SUSPICIOUS`/`SCAM` or `UNVERIFIED`; yes: queue WorkManager → send request → server auth/idempotency/slot → embed → search approved knowledge → Gemma JSON result with shadow rule evidence → [valid before deadline?] → yes: persist verified state and update/cancel warning → end; no: mark remote unavailable and keep provisional state → end. Show separate explicit historical-batch start, limited to participant-approved items.

## 5. Use Case Diagram and UC-1–UC-5 — Fig. 4.3.2.1, PDF pp.64–70 — P0

**Valid:** Partially: receiving SMS, viewing results, reporting, and viewing tips still exist. **Outdated components:** permission loading on-device Gemma; local threshold model invocation; report without raw SMS; server tip refresh. **Missing:** phone enrollment, AI Protection consent, revoke/renew, report-specific consent, historical small batch, `UNVERIFIED`/SUSPICIOUS display, optional study contribution and admin review. **Incorrect arrows:** reporting is an explicit user action, separate from automatic inference. **Storage/boundary correction:** use cases should assign Room to device and report/knowledge/study operations to server roles. **RAG/backend effect:** RAG is internal to server analysis, not a use case the mobile user invokes directly. Evidence: `A/view/fragment/OnboardingFragment.kt`; `A/view/fragment/MessageDetailFragment.kt`; `A/view/fragment/SafetyTipsFragment.kt`; `S/production/createProductionApp.js`; `S/admin-web/app.js`.

**Replacement specification:** Actors: Mobile User, Android OS, Controlled APCIDA Service, Admin/Researcher (study/admin cases only). User cases: grant SMS permission; enroll phone; enable/disable AI Protection; view inbox and result state; submit feedback after SMS-sharing consent; read local safety tips; choose small historical batch; optionally consent/submit study contributions. OS initiates received-SMS case. Service supports authenticated analysis and report receipt. Admin reviews reports and explicitly stages/approves knowledge. Update UC-1 precondition and remove model-load postcondition; UC-2 state table includes provisional/verified/unavailable; UC-3 conditional confidence/rationale; UC-4 actual report types/payload; UC-5 local-only tips. `A/view/dialog/ReportFormDialog.kt` and `S/production/reportContract.js` contain the exact reporting choices/contract.

## 6. Sequence Diagram — Fig. 4.3.4.1, PDF pp.70–71 — P0

**Valid:** No for beta. **Outdated components:** on-device Gemma 2B participant and startup loading. **Missing:** worker, per-install authorization, server, embedding model, knowledge repository, Ollama, result/error paths. **Incorrect arrows:** `keyword-score > threshold` does not gate remote request; raw SMS and sender actually cross HTTPS. **Storage/boundary correction:** Room is on phone; PostgreSQL holds RAG and encrypted response cache. **RAG/backend effect:** embed → vector search (top 3, >=0.72) → include retrieved examples in chat, even if zero hits, is required for beta server. Evidence: `A/backend/remote/ProductionSmsTransport.kt -> analyze`; `S/production/createProductionApp.js -> createAnalysisService`; `S/db/knowledgeRepository.js -> search`; `S/services/ollama.js -> analyze`.

**Replacement specification:** Participants left to right: Android OS → SmsReceiver → SmsController/BackendKeywordRules → Room → SmsProcessingWorker/Transport → authenticated production API → PostgreSQL knowledge/inference cache → Ollama embedding → Ollama Gemma 3 12B → Android UI/notification. Messages: SMS received; local score/store; optional immediate warning; eligibility check; POST with ID/text/sender/time; auth/claim; rules v3 shadow; embed; pgvector lookup; chat with examples; validate three-class response; encrypted cache; response; Room update; alert/cancel. `alt` blocks: gate closed/consent denied, no retrieval match, auth/revocation, database/embedding/model timeout, stale job. Add a **separate** report sequence: user consent → Room report snapshot → `/api/v1/reports` → encrypted `production_reports` → admin review.

## 7. Context Diagram — Fig. 4.3.5.1, PDF pp.71–72 — P0

**Valid:** No. **Outdated components:** on-device Gemma as an external actor, admin receiving only anonymized metadata. **Missing:** actual HTTPS service boundary, controlled Ollama, PostgreSQL, Cloudflare Access/per-install enrollment, admin dashboard and optional study route. **Incorrect arrows:** app sends raw SMS and sender for automatic beta analysis and raw SMS in reports; verified AI result returns. **Storage/boundary correction:** Android app encloses local rules, Room and worker; backend encloses API/RAG/model access and server stores. **RAG/backend effect:** RAG is inside the backend, not a phone-side actor. Evidence: `A/backend/remote/ProductionSmsTransport.kt`; `A/backend/network/ReportApiService.kt`; `S/production/createProductionApp.js`; `S/admin-web/app.js`.

**Replacement specification:** Central Android application boundary with Android OS/SMS source and User outside it. Adjacent public HTTPS tunnel/Access boundary into controlled API. Inside backend boundary draw Ollama (`gemma3:12b`, `nomic-embed-text`), PostgreSQL (`rag_knowledge`, inference/cache, reports, optional `study`), and admin dashboard as separate controlled interface. Arrows: OS → app SMS; User → app permissions/AI consent/report consent; app → API raw text+sender+time for eligible beta inference; API → app verified class/confidence/rationale or error; User/app → API consented report text; Admin ↔ reports/staging/approved knowledge. Mark routine inference cache as HMAC+encrypted response, not raw request storage (`S/production/privacy.js`; `S/db/migrations/004_production_inference.sql`).

## 8. ERD — Fig. 4.3.6.1, PDF pp.72–73 — P0

**Valid:** Partially for *local* entities only. **Outdated components:** local fields omit remote state, sender address and report text snapshot; five tables are called the full system. **Missing:** server RAG knowledge/staging/vector, production installations/inference/reports, invites, optional study schema. **Incorrect arrows:** `reports.message_id` is nullable with `ON DELETE SET NULL`, so report need not always retain a message FK; local `message_keywords` has cascade FKs. Report review does not automatically connect to RAG knowledge. **Storage/boundary correction:** draw **two ERDs**, one Room and one PostgreSQL, with a dashed API/data-flow connection instead of a cross-database FK. **RAG/backend effect:** approved knowledge and staging are related by `active_knowledge_id`, and vector similarity is a query, not a FK. Evidence: `A/model/entity/{Message,MessageKeyword,Report}.kt`; `S/db/migrations/001_rag_knowledge.sql`, `002_knowledge_workflow.sql`, `004_production_inference.sql`, `007_production_reports.sql`, `009_study_contributions.sql`.

**Replacement specification:** Local ERD: `messages(message_id PK)` ↔ `message_keywords(message_id FK, keyword_id FK)` ↔ `keywords(keyword_id PK)`; `messages` → `reports(message_id nullable FK SET NULL)`; `safety_tips` independent. Include `messages` remote status/source fields and `reports.sms_text_snapshot/consent_scope/is_sent`. Server ERD: `production_installations` → `production_inference_requests` and `production_rate_windows`, `production_reports`, `production_enrollment_invites`; `rag_knowledge_staging.active_knowledge_id` → `rag_knowledge`; optional `study.participants` → `study.batches`, `study.contributions` → `study.predictions` and `study.expert_labels`; `study.withdrawals` references installation. Use pgvector `vector(768)` and encrypted `bytea` types, not invented JSONB keywords. Full field audit: `MANUSCRIPT_DATABASE_AUDIT.md`.
