# APCIDA database and data-flow audit

Compared with §4.3.6 ERD (PDF pp.72–73), §4.4.1–4.4.2 (pp.73–78), Appendix A (pp.98–100), §3.8–3.10 (pp.43–51), and UC-4 (pp.68–69) of `Manuscript - ApCiDa (1).pdf`. Repository state and deployment caveat are in `MANUSCRIPT_GITHUB_GAP_ANALYSIS.md`. Path shorthand: `A/` = `.tmp-mobile-notification-fix/app/src/main/java/com/apcida/smishingdetector/`; `S/` = `apcida-ai-server/src/`. This is the **schema declared by code/migrations**, not a live database inspection; actual deployed migration level and row counts were not queried.

**Priorities:** P0 — correct the raw-SMS/report privacy claims, add the server database, and replace the ERD/data dictionaries before review. P1 — document status, consent, retention, indexes, and the local/server rule-version distinction. P2 — clarify seed and safety-tip update behavior. P3 — correct `sender_harsh`, field descriptions, and formatting after the substantive rewrite.

## On-device database — Room/SQLite

`A/backend/database/AppDatabase.kt -> @Database/getInstance()` declares database `kasds_database`, version 9, and exactly five Room entities: `messages`, `keywords`, `message_keywords`, `reports`, `safety_tips`. This is a correct *local* table count, but it is not the whole system. Migrations 1→3 through 8→9 are coded there; `exportSchema = false`. `A/backend/database/DatabaseSeeder.kt -> seedIfFirstLaunch()` seeds keywords and safety tips from `app/src/main/assets/keywords_seed.xml` and `safety_tips.xml`. Current beta SMS intake invokes `A/backend/detection/BackendKeywordRules.kt -> analyze()` directly, so a manuscript sentence saying the active beta engine queries the Room `keywords` table for every SMS is false (`A/controller/SmsController.kt -> receiveAndAnalyzeRules`). XML seeding remains implemented for the local tables/legacy features.

**Current local `messages` field inventory:** `message_id` PK; sender/content hashes and raw `sender_address`/`content`; source and alert fields; receive/create timestamps; rule/combined score fields; rule/AI/history/sender points; preliminary and final labels; matched indicators/contact/strong-signal flags; Gemma fields; AI/processing/detection/source states; remote request UUID, consent generation, notification state. Exact Kotlin names/types/defaults: `A/model/entity/Message.kt`; authoritative DAO updates: `A/backend/database/dao/MessageDao.kt`, `A/backend/repository/MessageRepository.kt`. Avoid converting nullable Kotlin properties into required SQL fields without inspecting generated Room schema.

**Current local `reports` field inventory:** `report_id` PK; nullable message FK; durable client UUID; report type/remarks; risk, Gemma class/rationale/confidence, final/rule verdict, process/AI status, matched indicator, SMS text, consent scope, app/model version snapshots; report time and sent flag (`A/model/entity/Report.kt`). `A/backend/reporting/ReportSnapshotFactory.kt -> create()` requires user consent and nonempty SMS <=4,000 characters. `A/backend/network/ReportUploadManager.kt -> uploadOne()` sends only `clientReportId`, `reportType`, `remarks`, `smsText`, `consentScope`, `observedVerdict`, `riskScore`; **it does not send the local matched-keyword list or model rationale in the current report API payload**. Do not confuse the local snapshot with the transmitted JSON.

**Score compatibility caveat:** active Android rules can sum to 105 (phrase cap 60 plus strongest URL score 45), but `S/production/reportContract.js -> validateReport()` accepts optional `riskScore` only from 0 to 100. `A/backend/network/ReportUploadManager.kt -> uploadOne()` therefore drops a local report score outside that range, while retaining the report. The manuscript should not call the report score universally present or imply a probability.

## Server database — PostgreSQL `apcida`

`S/config/env.js -> loadDatabaseUrl()` requires a local PostgreSQL database named `apcida`; `S/db/migrate.js -> shouldApplyMigration()` applies migrations 001–003 by default and 004–010 only with controlled production-schema opt-in. PostgreSQL has public-schema RAG, pilot/production identity, inference, and report tables, plus optional `study` schema. `rag_knowledge` uses `pgvector`, not a JSONB keyword table. `study.batches.response` is JSONB. Production server config and routes: `S/production/server.js`, `S/production/createProductionApp.js`. The tables below are schema-defined; `study` routes are conditional on `APCIDA_STUDY_ENABLED`.

`schema_migrations(version, checksum, applied_at)` is the migration-ledger table created by `S/db/migrate.js -> runMigrations()`; it is administrative schema state rather than SMS, report, or knowledge data.

## API payloads and privacy/data lifecycle

| Flow | Data crossing phone/server boundary | Persistent server record | Consent/gate | Evidence |
|---|---|---|---|---|
| Automatic supervised beta inference | `messageId`, **sender**, **raw `text`**, `receivedAt`; max sender 100 chars/text 2,000; authenticated request | `production_inference_requests` stores request HMAC, status/lease and encrypted **response**, not request text; retrieval/LLM processes text transiently | Explicit beta build, enrollment/credentials, approved HTTPS host, AI Protection consent, new SMS | `A/backend/remote/ProductionSmsTransport.kt -> analyze`; `S/production/smsContract.js`; `S/production/privacy.js`; `S/db/migrations/004_production_inference.sql` |
| Explicit user report | `clientReportId`, report type, remarks, **`smsText`**, `consentScope`, observed verdict, risk score; up to 4,000 text chars | `production_reports.content_encrypted` contains report JSON including SMS text; HMAC/status/time outside ciphertext | Separate checkbox/combined review and RAG-candidate consent plus per-install credentials | `A/view/dialog/ReportFormDialog.kt`; `A/backend/network/ReportApiService.kt`; `S/production/reportContract.js`; `S/db/migrations/007_production_reports.sql` |
| Optional study contribution | Participant-selected SMS text, local suggestion, batch counts/time and consent scope; input rejects common numeric/email patterns but does not prove anonymity | `study.contributions.content_encrypted`, HMAC and separate study metadata; `study.batches.response jsonb` | Separate `STUDY_EVALUATION_ONLY` batch contract; endpoint only if study feature enabled | `S/study/contract.js`; `S/study/repository.js`; `S/production/createProductionApp.js` |
| RAG knowledge curation | Reviewed candidate content entered by controlled admin workflow | Approved content and vector in `rag_knowledge`, staging data in `rag_knowledge_staging` | Human review/approval, dedupe/evaluation guard; no automatic report-to-RAG insert | `S/knowledge/batchReview.js`; `S/db/knowledgeRepository.js`; `S/production/reportReviewCli.js` |

The manuscript’s “raw SMS is never transmitted” statement is **false for consented automatic inference and reports**. “Anonymized report metadata” is also false: the API requires SMS text, and optional remarks may contain personal data. The server encrypts stored report content with AES-256-GCM and uses HMACs for deduplication (`S/production/privacy.js`), but this is encryption/pseudonymization, not anonymization. `S/production/reportReviewCli.js -> inspect()` explicitly permits a privileged reviewer to decrypt a report into a private file; `S/admin-web/app.js` exposes controlled review/staging screens. Report review does not itself add a RAG entry; approval is a separate step (`S/knowledge/batchReview.js`).

**Retention and deletion.** Routine inference cache defaults to 24 hours, configurable 1–72 hours (`S/production/server.js -> productionSettings`; `S/production/repository.js -> purge`). Report rows default to 30 days (`S/db/migrations/007_production_reports.sql`) and are purged by repository cleanup. Installation revocation deletes linked reports and study records (`S/production/repository.js -> revoke`; FKs). Study retention requires a separate configured value when enabled (`S/production/server.js`). State these as *configured/code-supported* behavior, not a guarantee about uninspected backups, logs, or live operations. No SQL keyword JSONB field was found; the only verified JSONB here is `study.batches.response`.

## Required corrected dictionary/ERD layout

1. **Figure 4.3.6.1a, Room:** five entities, all current `Message` and `Report` fields, `message_keywords` cascade FKs, nullable report message FK with SET NULL, `safety_tips` independent. Show `keywords` as seeded local data, without implying beta intake reads it.
2. **Figure 4.3.6.1b, PostgreSQL:** separate public schema (knowledge/staging, production identity/invites, inference/rate/slot, encrypted reports) and optional study schema. Label `vector(768)`, `bytea` encryption and `study.batches.response jsonb` accurately. Show HNSW/expiry indexes in notes, not as relationships.
3. **Cross-boundary flow, not a database FK:** Android raw-text inference and report/study JSON requests traverse authenticated HTTPS. The server returns a verified class/confidence/rationale or error; Android persists the resulting state in Room. Draw no direct Room-to-PostgreSQL foreign key.
