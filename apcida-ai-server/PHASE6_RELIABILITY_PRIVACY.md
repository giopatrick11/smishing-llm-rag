## Privacy observations from code

The phone sends message text, sender, receipt time, and message ID through Cloudflare to the Mac API for analysis. The controlled production tables store a keyed request digest and an encrypted response for replay, but no raw message text or sender field. The API audit function logs event name, installation ID, HTTP status, and elapsed time. Revocation deletes that installation's inference cache and rate windows. Cloudflare, Ollama, Android device logs, and any future backup need separate retention review before real SMS is enabled.

### Mac and Cloudflare log review (2026-11-01)

The controlled API writes only event name, installation ID, status code, and elapsed time in its production audit lines. The API does not use an HTTP request-body logger, and its error handlers return generic codes without printing SMS text. The Mac's LaunchAgents redirect API and tunnel output to four files in `~/Library/Application Support/ApCiDa/controlled-server/`. A read-only scan of those files found 60 API audit lines with installation IDs and five tunnel-log references to API paths, but no instances of the known synthetic message samples or credential-header names. This scan is limited to those samples and cannot prove that arbitrary future content will never enter a log. The files have mode `0644`, but both parent directories have mode `0700`, so other local accounts cannot reach the files through those directories. Neither LaunchAgent configures log rotation. The tunnel is using Cloudflare's default `info` log level; Cloudflare warns that `debug` can print request and response headers. Before real SMS, make file permissions owner-only as an additional guard, establish rotation and deletion periods, and keep tunnel debug logging off.

Cloudflare's [Zero Trust log retention table](https://developers.cloudflare.com/cloudflare-one/insights/logs/) currently lists 24 hours for Access and HTTP logs on the Free plan, with longer periods on some paid plans. [Access authentication logs](https://developers.cloudflare.com/cloudflare-one/insights/logs/dashboard-logs/access-authentication-logs/) record service-token access decisions; per-request logging is a separate dataset. [Tunnel logging documentation](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/) says the default local level is `info` and that `debug` logs request and response headers. These are product defaults, not a verification of the ApCiDa account's actual dashboard settings, Logpush jobs, or Log Explorer storage. Check both account- and zone-level Logpush pages, plus [Observability > Logs > dataset selector > Configure](https://developers.cloudflare.com/observability/logs/log-explorer/manage-datasets/), before real SMS is enabled.

The owner then showed the account Logpush subscription screen and the `apcida.stream` zone Logpush Jobs screen. The account screen offered a subscription rather than an existing job list; the zone screen explicitly showed `No Logpush jobs` and 0.00 GB exported this month. No Logpush destination is visible in those screens. The Logs dataset selector's `Add more datasets` action opened an `Activate Log Explorer` billing screen, confirming Log Explorer has not been activated in this account. No subscription or dataset was enabled.

Local diagnostics are now rotated by the user LaunchAgent `com.apcida.log-rotation` at 03:15 local time each day. The installed rotator copies each of the four API/tunnel log files into the owner-only `log-archive` directory, truncates the live files without changing their inodes, and deletes archives older than 30 days. The live files and archives are mode `0600`; the archive directory is mode `0700`. The first run archived two nonempty logs, and a manual LaunchAgent trigger exited 0. A separate temporary-directory check verified repeat rotation, file modes, 30-day pruning, and refusal of a symlinked log file. Copy/truncate can lose a line written in the narrow copy/truncate window, so these files are diagnostic rather than a complete request ledger. The API still answered HTTP 200 on its configured local port 3021 after installation; an earlier check against the old pilot port 3020 failed because that port is no longer used.
